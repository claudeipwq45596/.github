<p>需求表的四项内容：需要长期登录的账号数、集中在哪几个时段、峰值并发、需要覆盖的国家或城市。四项都写成数字，写不出来的先观察一周再谈。</p>

<h2>二、第 1 至 3 天：询价时问什么，别只问价格</h2>
<p>同一批参数问三到五家，问法一致才能比。只问价格的话，你拿到的是五个不同结构的报价，没法放在一张表里。</p>
<h3>五个必问参数</h3>
<p>一是地址归属：是运营商家宽段还是机房段，能否给 ASN 和 PTR 信息；二是复用情况：单条地址几个人用；三是并发定义：按连接数还是按活跃会话算；四是更换规则：被标记后是否免费换、多久一次；五是响应时效：工单多久回，是否有值班。五个问题里，第二和第四个最能筛掉不合适的。</p>
<h3>资料核对：官网写得越具体越可信</h3>
<p>看三处：是否写明节点所在城市、是否给出可查询的 ASN、价格页是否列出超量与保底。三处都模糊的，先放一放。反过来，愿意把测试地址直接给你的，通常在后两项上有底气。</p>

<h2>三、第 3 至 7 天：试用期怎么压，别只点开网页</h2>
<p>试用不是能不能打开页面，而是能不能在你最忙的时段保持稳定。压测至少覆盖一个工作日的高峰和一个夜间时段，两个时段的表现往往差别很大。</p>

<h2>四、第 2 周：小批量上线，看真实业务的表现</h2>
<p>试用期的压测是合成的，真实业务的请求形态更复杂。这一周的做法是把一到两成流量切到新出口，其余仍走原线路，两边都留日志，做同周期对比。</p>
<h3>对比看三个数</h3>
<p>成功率、P95 耗时、以及异常提示的出现次数。三个数只要有一个明显差于原线路，就先停下，不要急着放量。差异不明显时也别急着全切，再观察一周更稳。</p>
<h3>把运维动作演练一遍</h3>
<p>趁流量小的时候，把凭据轮换、白名单变更、备用线路切换各演练一次，记录耗时。这几件事在真正出问题时才第一次做，代价会大得多。</p>

<h2>五、第 3 至 4 周：放量与续费决策</h2>
<p>放量的节奏是每周翻一倍，每次只改一个变量。翻倍之后观察 48 小时，稳定再翻。急着一周切完，出问题时无法判断是哪一步引入的。</p>
<h3>续费前要回看的三条</h3>
<p>一是这一个月里有没有发生过影响业务的中断，持续多久、谁处理的；二是账单与预估差多少，差在流量还是并发；三是工单的首次响应时间是否在承诺范围内。三条都过关，续费；有一条不过关，先谈条件再续。</p>
<h3>什么情况下该换</h3>
<p>不要因为一次波动就换。判断标准是同类问题是否重复出现、供应商是否给出了可执行的改进方案。重复出现且方案含糊，换的成本通常低于继续忍的成本。</p>

<h2>常见问答</h2>
<h3>试用期一般给多久？</h3>
<p>答：常见是 1 到 3 天，也有按流量给试用量。时间短就要提前把压测脚本准备好，拿到账号当天就跑，别把时间花在配置环境上。若只给几小时，建议先测高峰时段。</p>
<h3>同时试多家会不会更麻烦？</h3>
<p>答：会麻烦一点，但值得。两到三家并行试，用同一套脚本、同一时段，结论才有可比性。只试一家的话，你无法判断它究竟是"够用"还是"最好"。</p>
<h3>供应商说节点很多，怎么核实？</h3>
<p>答：要几条不同城市的测试地址，自己查 ASN 和 PTR，再看延迟。节点数量本身不是指标，你需要的那个城市有没有稳定的出口才是。</p>
<h3>合同里最该盯哪一条？</h3>
<p>答：更换与退款条款。地址被标记后多久能换、换几次、不满意能否按剩余天数折算退款，这三项写清楚，比 SLA 里的百分比更实际。</p>
